# 장애 진단 종합

## 1. 장애 진단은 이렇게 한다.

### 1-1. 진단 요청을 받았을 때 가장 먼저 할 일

 - 장애 유형 확인
 - 시스템 기본 정보 확인
 - 각종 데이터를 통한 원인 진단
 - 원인이 발견되었을 경우, 장애 원인 제거 후 확인
 - 진단 결과 보고서 작성

진단할 때 가장 먼저 해야 할 일ㅇ느 장애의 유형을 살펴보는 것이다. 정확히 어떻게 느린지에 대한 확인 절차가 필요하다.  
그 다음에 해야 하는 작업은 시스템에 대한 정보를 얻는 것이다. 어떤 환경인지, 시스템을 분석할 수 있는 근거 자료는 얼마나 있는지에 대해 알아본다.  
이러한 정보들을 얻었다면, 시스템에 들어갈 수 잇는 권한이 있어야만 한다. 알아야만 하는 정보 중에서 가장 중요한 것은 서버에 로그인할 수 있는 계정과 작업할 장소의 IP다.  

 - 장애 현상
    - 어떤 문제가 발생했는지에 대한 정보
 - 모니터링 시스템
    - 모니터링 시스템 여부
    - 모니터링 시스템의 URL 또는 접근 방법 확인
 - Java 정보
    - 자바 버전
    - JDK 설치 위치
 - 웹 서버 정보
    - 웹 서버 종류
    - 웹 서버 설치 위치
    - 웹 로그 위치
 - WAS 정보
    - WAS 종류
    - WAS 설치 위치
    - WAS 설정 파일 위치
    - 도메인 설치 위치
    - 로그 파일 위치
 - DB 정보
    - DBMS 종류
    - DB 설치 위치
    - DB 관련 설정 파일 위치
 - 기타 정보
    - 연계 시스템 여부
    - 연계 시스템 위치
    - 각 서버의 로그인 계정
    - 작업할 장소의 IP

### 1-2. 본격적인 진단 시작하기

#### 해피 케이스

 - 모든 시스템에 대해서 잘 알고 있는 담당자가 있는 경우
 - 모니터링 도구가 있는 경우
 - 각종 로그가 잘 쌓여져 있는 경우

#### 진단 원인 찾기

작업의 흔적을 남기는 것은 중요하다. 어떤 정보들을 확인했는지, 어떤 정보들이 의심이 되는지를 정리해 놓는다.  
원인을 찾았을 때 또 한 가지 중요한 점은, 장애를 재현시키는 것이다. 장애 상황을 재현하면 문제점을 찾아낼 수 있는 확률이 높아진다. 그리고 문제점을 수정한 후에 장애 상황을 재현시키는 작업을 해서 문제점을 완벽히 해결해야만 한다.

### 1-3. 장애 원인 제거하고 결과 정리하기

장애의 원인이라고 지목한 부분을 수정하였으면, 반드시 운영 서버에 문제가 없는지 확인하고, 장애가 정말 사라졌는지 지켜봐야 한다.  
장애 원인을 제거하였다는 판단이 서면, 관련 팀이나 인원에게 이 사실을 통보하고 보고서 정리 작업을 수행한다. 만약, 본인이 운영하는 시스템이라서 거창하게 보고서를 따로 작성할 필요가 없다고 판단될지라도, 간단하게 워드나 위키에 정리하는 것을 추천한다. 동일한 장애가 다시 발생하지 않는다는 보장이 없고, 다음에 동일한 문제를 겪을 분들을 위해서 이 작업은 필수다.  

```
★ 증상
20XX년 XX월 XX일 14시 20분 갑자기 화장실에 가고 싶은 상황이 발생하였음.

★ 원인
점심 먹고 먹은 아이스크림이 문제인 것으로 판단됨
그 다음에 먹은 우유도 문제가 될 수 있음

★ 해결 방안
화장실로 직행
양호실에 가서 소화제를 받음
상황이 더 안 좋아질 경우를 대비하여 조퇴하여 병원으로 직행
```

# 1. 개요
한 달 뒤, 1년 뒤에 보더라도 이 보고서에 있는 작업을 언제 왜 했는지, 누가 보더라도 이해하기 쉽게 작성해야 한다.

A. 장애의 증상과 시기
장애가 언제 왜, 어떻게 발생했는지에 대해서 정리

B. 장애가 발생한 서버의 스팩과 사용 중인 소프트웨어의 버전
제 3자의 이해를 돕기 위해 해당 시스템의 배경 상황을 정리

C. 진단에 참여한 인원, 진단 기간, 사용한 도구
누가, 어떤 방법으로, 얼마나 오랜 기간 동안 진단 작업을 수행했는지 정리한다.

D. 기타 각종 상황
그 외에 장애 상황에 대한 여러 가지 정황들을 기재해 두면 많은 도움이 된다.

# 2. 진단 내역 및 원인
A. 가장 효과가 많은 부분부터 작성
IT 회사에 다니는 사람이면 누구나 이해할 수 있도록 쉽게 작성해야 한다.

B. 진단은 했지만, 문제가 없었던 부분은 필요할 경우 작성
그 부분은 확인해 본 결과 큰 영향은 없었음 이라는 코멘트라도 적어주는 것이 좋음

C. 장애의 원인
만약 소스가 있다면, 정확하게 어느 부분이 문제라고 찍어주는 것이 좋다.
'이 부분에 대한 필요성 확인 요망' 등의 코멘트 사용

# 3. 해결 방안
A. 반영 전과 후의 차이를 쉽게 확인할 수 잇는 수치나 그래프로 표시

백 마디 말보다 숫자로 정리한 표 혹은 그래프로 표시하는 것이 좋다.

B. 필요에 따라서는 수정한 소스 코드나 수정 후 로그 파일의 내용도 포함
필요할 경우에 한해서 정리해 놓는 것도 좋음
